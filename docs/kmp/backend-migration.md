# Native API migration and rollback

Production backup and release were explicitly authorized and executed on 2026-10-21; see [the release record](production-release-2026-10-21.md) for backup verification, deployed version, rollback guidance and remaining Access/R2 gates. Migration is additive and requires the existing Cloud Mail initialized/current schema (`email`, `account`, `attachments`, `star`, `user`). Review `mail-worker/migrations/0001_app_v1.sql` and export a D1 backup before applying in an isolated staging environment, then production during an approved release.

Local/staging command: `npx wrangler d1 migrations apply <database-name> --local --config <local-config>`. Production requires separately authorized `--remote` use. All native tables and indexes are prefixed `app_`; existing data/columns are preserved. Legacy intake, Web actions, webhook status writes, ownership changes, physical cleanup and attachment changes are captured by SQLite triggers inside the original transaction. Seeding records existing email IDs once. Reapplying migration does not erase cursors or duplicate seed events.

Rollback application code first; disable native clients. Drop only the `app_*` triggers from sqlite_master, then optional `app_*` indexes/tables after exporting sessions/actions/send-operation evidence. **Never delete email/account/attachments/star/user tables or change MX.** Backward application rollback does not undo legitimate emails sent or user actions; provider delivery is irreversible. Keep send-operation records until support reconciliation is complete. Native clients must clear their cursor on migration epoch change and resynchronize; never reuse old cursor after rebuilding log. Existing Web sessions remain untouched throughout.

Release gate: privately serve attachments through Worker. Any previously public `r2Domain`/S3 bucket can expose objects independently of Worker authorization; making the bucket private requires operator configuration. Keep `/static/background/*` public. Updated Web retrieves private attachments and inline pictures with its raw JWT into temporary Blob URLs. Old cached Web bundles must be refreshed together with private attachment route deployment.

Capacity: v1 change log and operation ledger are deliberately append-only for correctness. Monitor size/write amplification (account ownership/deletion edits emit events for its mail). Do not prune without cursor-retention protocol and signed epoch rollover. Expired rate buckets are bounded opportunistic-cleaned; expired sessions can be removed through an operational retention job. Database maintenance is operator approved.

Password verifier bridge: the initial repository used salted single SHA256. New/reset credentials now use `pbkdf2-sha256$100000$` with a random salt and Cloudflare-compatible PBKDF2-SHA256 work factor; verifier still accepts legacy stored hashes. Existing credentials are not silently rewritten. Backport the dual-format verifier before rolling back to an older Worker after any new/reset password was saved, otherwise old code cannot verify that new format. Never downgrade password hashes or request all users reset. Operator-reviewed future opportunistic migration can remove legacy hashes after a compatible rollback window.
